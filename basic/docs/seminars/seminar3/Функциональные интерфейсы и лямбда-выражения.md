# Функциональные интерфейсы и лямбда-выражения

*Слайды 3–16 презентации «Семинар 3».*

---

## Что такое функциональная парадигма

Три столпа, по которым удобно сверяться (слайд 4):

- **Декларативный подход.** Описываем *что* сделать, а не *как* — пайплайны обработки данных вместо циклов с
  ручным управлением.
- **Immutability.** Данные неизменяемы: чтобы «изменить» значение, создаём новую копию, а не мутируем старую.
- **Pure functions.** Результат зависит только от аргументов (одинаковый вход — одинаковый выход), без побочных
  эффектов на внешнее состояние.

Ещё одна опора ФП — **функции как объекты первого порядка**: их можно сохранять в переменные и передавать в другие
функции («функции высшего порядка»). В представлении Алана Кея это вообще-то и есть чистое ООП — не противоречие,
а вопрос того, что именно считать «объектом».

**А как же Java?** (слайды 6–8) Все три идеи в Java *есть*, но не гарантированы языком, а держатся на дисциплине
разработчика:

| |Java|Строго функциональный язык (Haskell)|
|---|---|---|
|Парадигма|ООП с имитацией функционального подхода в ограниченном масштабе — обычный код, ФП по необходимости|Функциональный по умолчанию, к которому нужно (с болью) привыкать|
|Функция как объект|Есть, но под капотом — объект функционального интерфейса (синтаксический сахар)|Функция как объект первого порядка — часть модели языка|
|Неизменяемость|Самодисциплина и принцип: без `final`/иммутабельных структур никто не помешает мутировать|Гарантия языка|
|Типизация|Строгая, но с явным выводом типов там, где можно|Строгая|

Java — не первый язык, где ФП не единственная парадигма: даже Scala объединяет в себе ФП и ООП. Из чисто
функциональных языков — Lisp, Haskell; JS — отчасти (функции первого порядка есть, чистота и неизменяемость —
только по соглашению, как и в Java).

## Как писали код до Java 8

До синтаксического сахара 1.8 у функционального интерфейса было ровно два способа реализации — полный класс или
анонимный класс. Обе задача: проверить, что валюта инструмента равна переданной.

```java
class CurrencyMatcher implements Predicate<Instrument> {
    private final Currency currency;

    CurrencyMatcher(Currency currency) {
        this.currency = currency;
    }

    @Override
    public boolean test(Instrument instrument) {
        return instrument.getCurrency() == currency;
    }
}
```

```java
Predicate<Instrument> matcher = new Predicate<Instrument>() {
    @Override
    public boolean test(Instrument instrument) {
        return instrument.getCurrency() == currency;
    }
};
```

Нас волнует одна строка — «возьми `currency` с инструмента и сравни с переданной», а написать пришлось имя класса,
сигнатуру метода, `@Override` и фигурные скобки. С лямбдой — то же самое одной строкой:

```java
Predicate<Instrument> matcher = instrument -> instrument.getCurrency() == currency;
```

## Функциональный интерфейс

Интерфейс с ровно одним абстрактным методом (SAM — *single abstract method*). Методов с реализацией по умолчанию
(`default`) при этом может быть сколько угодно — на SAM это не влияет, потому что у них есть тело, реализовывать
нечего. Классический пример — `Function<T, R>`.

Сопоставление с тем, что уже писали на семинаре 2, — анонимный класс `Iterator` в `InMemoryInstrumentRepository`:

```java
@Override
public Iterator<Instrument> iterator() {
    return new Iterator<>() {
        private int cursor = 0;

        @Override
        public boolean hasNext() {
            return cursor < size;
        }

        @Override
        public Instrument next() {
            if (!hasNext()) {
                throw new NoSuchElementException();
            }
            return instruments[cursor++];
        }
    };
}
```

`Iterator<T>` объявляет два абстрактных метода (`hasNext()` и `next()`) — это не функциональный интерфейс, лямбдой его
не переписать. Лямбда годится только там, где абстрактный метод ровно один.

**`java.util.function`:** `Predicate<T>` (`boolean test(T)`), `Function<T, R>` (`R apply(T)`), `Supplier<T>`
(`T get()`), `Consumer<T>` (`void accept(T)`) — структурно совпадают со своими доменными аналогами, поэтому в
большинстве случаев не нужно объявлять собственный функциональный интерфейс. Лямбды одного и того же вида можно
соединять в пайплайн через `.andThen(...)`/`.compose(...)` (`Function`) или `.and(...)`/`.or(...)`/`.negate(...)`
(`Predicate`) — практика этого приёма на реальном коде проекта, `ListFilterBuilder`, — на этапе 3.

## Ограничения лямбд

**Java не защищает от мутации внешнего состояния.** Лямбда, захватившая ссылку на изменяемый объект (например,
список), может изменить его содержимое — компилятор это не запрещает, в отличие от переприсваивания самой
захваченной переменной (см. ниже). Аккуратность с тем, что именно захватывает лямбда, — забота разработчика, а не
языка.

**Только *effectively final*.** В лямбда-выражениях доступны все переменные и поля из родительской области видимости
(включая ссылку на `this`), но только пока они `final` или *effectively final* — то есть не переприсваиваются после
инициализации:

```java
void example() {
    Currency currency = Currency.RUB;
    Predicate<Instrument> matcher = instrument -> instrument.getCurrency() == currency;
    currency = Currency.USD; // ошибка компиляции: currency больше не effectively final
}
```

Причина — не техническое ограничение синтаксиса, а следствие того, как именно лямбда реализована на уровне JVM (см.
ниже).

## Байткод: лямбда vs анонимный класс

**Анонимный класс компилируется в отдельный `.class`-файл.** Для `InMemoryInstrumentRepository` из семинара 2 в
каталоге сборки появляется файл `InMemoryInstrumentRepository$1.class` — компилятор сгенерировал именованный вложенный
класс, реализующий `Iterator<Instrument>`, ещё на этапе компиляции. Этот класс существует физически, как байт-код на
диске, до запуска программы.

**У лямбды нет `.class`-файла на этапе компиляции.** В байт-коде класса, где лямбда написана, вместо ссылки на
отдельный класс встретится инструкция `invokedynamic`:

```
0: invokedynamic #7,  0             // InvokeDynamic #0:test:(Lacademy/backend/market_pulse/model/Currency;)Ljava/util/function/Predicate;
     ...
private static boolean lambda$byCurrency$0(Currency, Instrument);
    Code:
       0: aload_1
       1: invokevirtual #12  // Method Instrument.getCurrency:()Lacademy/backend/market_pulse/model/Currency;
       4: aload_0
       5: if_acmpne     12
       8: iconst_1
       9: goto          13
      12: iconst_0
      13: ireturn
```

Тело лямбды компилятор превращает в обычный приватный статический метод самого класса (`lambda$byCurrency$0`) —
никакого нового класса на диске для этого не создаётся. Байт-код в месте, где лямбда *используется*, содержит
`invokedynamic` — инструкцию, которая при **первом** выполнении вызывает bootstrap-метод
`java.lang.invoke.LambdaMetafactory.metafactory`. Этот метод генерирует реализацию функционального интерфейса **во
время выполнения**, используя скрытый класс (`hidden class`, механизм `MethodHandle`), и связывает `invokedynamic` с
этой реализацией — при повторных вызовах генерация уже не происходит, связывание кэшируется.

**Следствие для effectively final.** Захваченные переменные передаются в синтетический метод как обычные аргументы —
по значению, в момент вызова. Если бы исходная переменная могла измениться после создания лямбды, метод в принципе не
смог бы понять, какое значение подставлять: он получает копию на момент вызова `invokedynamic`, а не связь с
переменной. Ограничение effectively final — не искусственное синтаксическое правило, а прямое следствие того, как это
устроено.
